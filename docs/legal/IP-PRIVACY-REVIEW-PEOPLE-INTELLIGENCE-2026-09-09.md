# People Intelligence IP and Privacy Review (2026-09-09)

## Scope

This draft review covers the public `skills/people-intelligence/` package, its fictional source-to-output scenario, focused test, governed documentation, catalog update, and generated IP inventory entries. It does not approve data collection, connector configuration, an external service, merge, release, or publication.

## Authoring provenance

The private golden implementation informed reusable workflow stages, evidence limits, conditional branches, output fields, failure behavior, and useful example depth. Public text, templates, tests, documentation, and fictional sources are newly authored for this repository. No private output, person, organization, message, identifier, source configuration, local path, or private-to-fictional mapping is included.

## Privacy and safety design

The package limits use to consented or otherwise authorized professional collaboration context. It excludes sensitive attributes, personal-life material, protected characteristics, employment evaluation, personality claims, surveillance, account scraping, voice imitation, automatic persistence, and external actions. The adopter owns evidence authority, permissions, retention, access control, correction, deletion, and any local output destination.

## Fictional example review

The fictional scenario uses independently invented people, organization, observations, dates, dependencies, and outputs. Its only web address uses a reserved `.invalid` domain. The completed brief cites its fictional evidence corpus and labels its inference. It is not an anonymized operating record.

## IP disposition

The scoped artifacts are project-authored documentation, templates, configuration, and tests suitable for the repository's Apache-2.0 contribution terms, subject to validation, sanitization scanning, review of the full candidate, and project-owner approval. The generated `IP-INVENTORY.csv` remains the per-file inventory record.

Automated scanning cannot prove that narrative is non-identifying or that an adopter has appropriate authority. Before merge, maintainers must review the full candidate for semantic leakage, run the required validation suite and private-denylist scan, confirm manifest-only changes, and keep this review Draft until the exact pull-request revision receives project-owner approval.
